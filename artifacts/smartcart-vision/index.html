Why edge inference

The model runs in-browser via TensorFlow.js. Streaming raw video from hundreds of in-store cameras to the cloud is bandwidth-prohibitive. The PM decision is what to compute locally vs. escalate — the same signal-prioritization tradeoff at scale.

Detection trust = adoption

The confidence threshold is the operating point on the precision/recall curve. Too low floods the cart with false adds; too high misses real items. Where you set it is a business decision about customer trust and shrink — not just a technical one.

What production adds

A real system swaps COCO's 80 generic classes for a retail-specific model, fuses multiple camera angles to handle occlusion, and escalates low-confidence events to a cloud reasoning layer (a Vision-Language Model) for the hard edge cases.

How this prototype works

When you start the camera, each video frame is passed to COCO-SSD — a convolutional neural network with a MobileNet v2 backbone — running locally through TensorFlow.js. The model returns a list of detected objects, each with a class label, a bounding box, and a confidence score. The app draws those boxes on an overlaid canvas, then applies a small amount of product logic on top.

Camera framegetUserMedia → CNN detects objectsCOCO-SSD on-device → Confidence filterthreshold slider → Debounce + presence logictrust safeguards → Virtual cartadd / remove items

Two pieces of logic make it behave like a real store rather than a flickery demo. A debounce requires an item to appear for several consecutive frames before it's added — this suppresses momentary false detections. A presence timeout removes an item only after it has been gone from view for over a second — so brief occlusion (a hand passing over a product) doesn't drop it from the cart. Both are deliberate trust safeguards, not happy-path shortcuts.

The key control — precision / recall tradeoff

The confidence slider sets the model's operating point on the ROC curve. Lowering it catches more items but admits false adds (higher recall, lower precision); raising it is safer but misses real items (lower recall, higher precision). In a real checkout-free store, where you set that threshold is a business decision about customer trust and inventory shrink — the same tradeoff you'd read off a precision/recall curve in a product review.

A short history of how machines learned to see

Computer vision didn't start with deep learning. It's the product of six decades of work, and the breakthrough ideas trace back further than most people expect — to a pair of neuroscientists studying cats.

1959–1962 · The Biology
Hubel & Wiesel — orientation-selective neurons
Recording from a cat's primary visual cortex, they found individual neurons that fire only for a line at a specific angle, or motion in a specific direction. Vision is built hierarchically: simple features first, combined into complex ones layer by layer. They won the 1981 Nobel Prize in Physiology — and unknowingly wrote the blueprint for the CNN.
1980 · The Architecture
Fukushima's Neocognitron
A neural network directly inspired by Hubel & Wiesel's findings, stacking layers of simple and complex feature detectors. No backpropagation yet — weights were hand-tuned — but the structural insight was right. The conceptual ancestor of every CNN that followed.
1989–1998 · The Method
LeCun's LeNet — learning the filters
Yann LeCun combined convolution with backpropagation so the network could learn its feature detectors from data, instead of having them hand-designed. LeNet read handwritten digits on real bank checks — the first CNN doing useful work at scale. The key idea: don't specify what features to look for, let the network discover them.
2012 · The Explosion
AlexNet wins ImageNet
A deep CNN trained on GPUs crushed the ImageNet Large Scale Visual Recognition Challenge, cutting the previous error rate roughly in half and beating every hand-engineered approach. It kicked off the modern deep-learning era of computer vision — the field changed overnight.
2015–2016 · Real-Time Detection
SSD & YOLO — fast single-shot detectors
Earlier detectors (R-CNN family) were accurate but too slow for live video. SSD (Single-Shot MultiBox Detector) and YOLO (You Only Look Once) detect and localize many objects in a single forward pass — fast enough for real-time video. This prototype runs exactly that lineage: COCO-SSD uses the SSD architecture with a lightweight MobileNet v2 backbone optimized for the browser.
2020–2026 · Attention & Reasoning
Vision Transformers and Vision-Language Models
Transformers — originally built for language — replaced convolution's local sliding window with global self-attention, letting a model relate every part of an image to every other part at once. Vision-Language Models (VLMs) go further, reasoning about images in natural language ("is this shelf compliant with the planogram?") rather than just classifying them. The 2026 frontier is hybrid CNN-plus-transformer pipelines: fast CNNs for dense detection, transformers for context and reasoning.

How a CNN actually sees

A CNN's core operation is the convolution: a small grid of learnable numbers (a filter) slides across the image pixel-by-pixel. At each position it multiplies itself against the pixel patch underneath and sums the result into a single number. One filter might learn to detect vertical edges, another horizontal ones — exactly like a Hubel-Wiesel orientation-selective neuron. The output is a "feature map" showing where that pattern appears in the image.

Stack these layers and the features grow in sophistication:

  • Early layers detect edges, color transitions, and angles — low-level primitives.
  • Middle layers combine those into corners, textures, curves, and simple shapes.
  • Deep layers assemble shapes into object parts, then into whole objects — "this is a bottle."

Between layers, pooling downsamples — keeping the strongest signal in each small region, so the network becomes robust to small shifts in position and scale. Because the same small filter is reused at every location across the whole image (weight sharing), CNNs use far fewer parameters than a fully-connected network would. That efficiency is why one runs live, in-browser, on a webcam feed without a GPU.

CNNs vs. human vision

CNNs were inspired by biology but differ from it in important ways. Human vision is predictive — the brain constantly generates a model of the expected scene and checks incoming light against that prediction (which is why optical illusions fool us; they satisfy the prediction while violating the ground truth). It is selective — a tiny high-resolution fovea darts around a scene in rapid saccades rather than processing all pixels equally. And it carries a world model — you know an object still exists when it's hidden behind another (object permanence). A CNN, by contrast, is purely feedforward: it processes every pixel equally in one pass, has no memory between frames unless you explicitly add it, and doesn't predict — it classifies. The frontier in 2026 is closing that gap by pairing fast CNN detection with transformer-based reasoning that begins to approach human-like context and understanding.

Why this matters for unattended retail

The winning architecture for a real checkout-free store is a hybrid: lightweight CNNs at the edge — on the camera itself — for fast, cheap, high-throughput detection; and a cloud reasoning layer (a VLM) that only sees the hard cases: obscured barcodes, new products, ambiguous hand-offs. That mirrors the edge-vs-cloud signal prioritization problem that appears at scale across any system with millions of sensing endpoints: you cannot move all the raw data, so you decide intelligently what to compute locally and what is worth the cost of escalating.

◈ Developer Notes

File structure

The entire app lives in a single file: artifacts/smartcart-vision/index.html. There is no build step, no bundler, and no npm dependencies. The page loads TensorFlow.js and COCO-SSD from CDN, then all logic runs in the inline <script> block at the bottom of the file. CSS is in a single <style> block in <head>. Supporting files (public/favicon.svg, public/manifest.json) provide the app icon and PWA install metadata only.

How to add a new item to the cart

Open index.html and find the SKU_MAP object. Add one line:

'coco class name': { price: X.XX, icon: '🆕', label: 'Display Name' },

The key must be an exact COCO-SSD class name (all lowercase, spaces allowed — e.g. 'cell phone', 'sports ball'). Reload the page. If the model detects that class, it will now appear in the cart with the price you set. Items not in SKU_MAP are still detected and boxed (grey), but are not added to the cart.

Tuning detection sensitivity

Two constants in the DETECTION CONSTANTS section control how aggressively items are added and removed:

  • ADD_FRAMES (default: 7) — number of consecutive video frames an item must appear in before it is added. At ~30 fps this is ~230 ms. Increase to reduce false adds; decrease for faster response.
  • PRESENCE_TIMEOUT (default: 1500 ms) — how long an item can be absent from frame before it is removed from the cart (Cart Mode only). Increase if items flicker out during occlusion; decrease for snappier removal.
  • The confidence slider in the UI controls confThreshold (default 60%). This is the precision/recall operating point — lower catches more items but admits false detections; higher is more conservative.

Scanner Mode vs. Cart Mode — state machine

The app has two modes, toggled by the mode button. Internally they share the same detectLoop() but diverge in how confirmed items are stored and displayed:

  • Cart Mode (default): items are tracked in the cart Map (class → { conf, lastSeen }). Each frame, lastSeen is refreshed for visible items. The presence-timeout pass removes any item whose lastSeen is older than PRESENCE_TIMEOUT. The cart mirrors what is currently in frame.
  • Scanner Mode: confirmed items are written to scannerTotals (class → { qty, conf }) and never removed by the timeout. The cart Map is still used as a "currently visible" tracker so the same physical item is not re-counted while it stays in frame — but once it disappears and reappears, cart is clear of it and it can be scanned again (qty increments). "Clear Cart" resets all three Maps (cart, pending, scannerTotals). 
Cart Mode state:
  pending[cls]++  each frame  →  if count ≥ ADD_FRAMES → cart.set(cls, {...})
  presence pass each frame    →  if now - lastSeen > TIMEOUT → cart.delete(cls)

Scanner Mode state:
  same ADD_FRAMES gate        →  scannerTotals[cls].qty++  (permanent)
  presence pass               →  cart.delete(cls) only (so it can be re-scanned)
  renderCart reads scannerTotals, not cart

Single-file architecture rationale

The no-build-step design is intentional for a demo: it makes the prototype trivially shareable (one file, any static host, opens from disk), removes all toolchain friction, and keeps the entire implementation readable in a single scroll. The tradeoff is that scaling to a real product would require splitting concerns — separate JS modules, a proper model-serving layer, and a backend cart/session API. Those are the right next steps for a production system, but wrong for a prototype where speed of demonstration is the priority.

Privacy Policy

Effective date: June 2026 · Last updated: June 2026

What we collect

SmartCart Checkout collects a small amount of anonymous, non-personal session data when you use the app. Specifically:

  • Session ID — a random UUID generated in your browser and stored in sessionStorage. It is cleared automatically when you close the tab or browser window. It is not linked to your identity in any way.
  • Event type — one of: session_start, camera_started, item_added, scanner_mode_toggled, session_end.
  • Browser user-agent string (truncated to 200 characters) — used only to understand what browser versions are in use.
  • HTTP referrer — the URL of the page that linked to this app, if any.

We do not collect video, images, or frames from your camera. All object detection runs entirely on your device via TensorFlow.js. No visual data ever leaves your machine. We do not collect your name, email, IP address, or any personally identifying information. No cookies are set — ever.

How it is stored

Session events are stored in a Replit-managed PostgreSQL database. The database is not shared with or sold to any third party. No advertising or analytics platforms (Google Analytics, Mixpanel, etc.) are used.

Retention

Session records are retained for 90 days and then permanently deleted.

Who can access the data

Only the app owner can query the database directly, using Replit's built-in database tooling. No one else has access.

AI and third-party services

No third-party AI services are used. Object detection is performed by the COCO-SSD / MobileNet v2 model, which runs entirely in your browser via TensorFlow.js. The model weights are fetched once from a public CDN (cdnjs.cloudflare.com / cdn.jsdelivr.net) and cached locally by your browser.

Your rights (GDPR / CCPA)

Because we store only anonymous session IDs and no personal data, there is nothing that can be traced back to you. If you believe a session ID generated from your browser session is stored and you wish it deleted, you may request deletion by emailing privacy@smartcart-checkout.example. We will process the request within 30 days.

No cookies

This app sets no cookies of any kind. The session ID lives only in sessionStorage — a browser storage mechanism that is scoped to the current tab and erased when you close it. No consent banner is needed.

Summary

Camera stays on your device. No personal data collected. No cookies. Anonymous session events stored for 90 days. Not shared with anyone.
